2026年4月29号，theori公开披露了漏洞Copy Fail (CVE-2026-31431)。该漏洞可以在自2017年以来几乎所有的Linux发行版上的本地稳定提权。

该漏洞发生在内核authencesn加密模块模板中的逻辑漏洞，通过AF_ALG套接字和splice()链式调用，赋予非特权用户对任何可读取文件的页面缓存进行确定性4字节写入的权限。xint公开了一个732字节的利用脚本，通过修改/usr/bin/su实现权限提升，并且不依赖任何条件竞争和符号地址。

本文将对漏洞发现过程，漏洞根因以及未来检测此类漏洞的思路进行简要分析。

漏洞发现过程#

在Copy Fail披露之前，Linux内核稳定提权工具还只有DirtyCow和DirtyPipe。时隔4年又一稳定提权漏洞被发现，theori声称该漏洞由他们自己开发的漏洞检测智能体Xint发现。

漏洞的发现者Taeyang Lee在早前针对kernelCTF的工作中对AF_ALG攻击面有了一定的研究。于是，Theori将该子系统作为Xint对Linux内核的尝试起点。根据公开博客所说，他们提供给智能体的提示词很简单：

This is the linux crypto/ subsystem. Please examine all codepaths reachable from userspace syscalls. Note one key observation: splice() can deliver page-cache references of read-only files (including setuid binaries) to crypto TX scatterlists.

从整个漏洞发现过程中，我们并没有得到多少有关智能体细节的信息。从提示词中，可以看到其中给出了较为明确的注意点。仅从展示的漏洞报告中，可以看到这似乎是一个静态代码审计的智能体，我们无法看到是否存在动态验证的部分。

最近，我也尝试使用AI去挖掘漏洞，其中一个尝试使其重点关注crypto模块，但仅关注内存安全问题。在Copy Fail公布后，我再次检查了AI的发现结果，发现其多次在AF_ALG部分尝试，甚至多次提到“TX/RX SGL”、“aead_recvmsg()”等，但是由于PoC无法通过KASAN进行动态确认，AI逐渐放弃该部分。Xint的报告仅有静态分析，并没有提到在一轮审计后存在多少误报率，以及多少漏洞需要人工验证，人工需要对目标模块了解到多少程度。这代表尽管Xint发现了如此具有影响力的漏洞，模型自身能力或许占了较大功劳，而后续漏洞的确认、分析则依然需要对目标有一定了解的专业人员介入。

漏洞根因与原理#

retr0针对该漏洞的背景知识给出了非常细致的介绍，下面主要是对其文章的中文翻译，并带有一些个人片面的理解。

The Page Cache#

每次我们对文件调用 read() 并且不带O_DIRECT标志时，内核通常并不会直接访问磁盘。它访问的是 page cache（页缓存）——这是一个系统范围的、驻留在内存中的文件数据缓存，按 (inode, offset) 键值对组织。

如果某个页面之前已经被任何进程读取并缓存过，内核就会直接从缓存返回数据。否则，内核会先从磁盘读取数据，将其放入缓存，然后再返回给调用者。

这里有两个关键的数据结构：

  • struct page：表示一个物理页（通常为 4096 字节）。它包含一些标志位、一个 mapping 指针（指回文件对应的 address_space），以及一个 index（该页在文件中的偏移量，以页为单位）。

  • struct address_space：与一个 inode 关联，负责维护这个文件在内存里的page cache。其中的i_pages字段是一个 XArray，用于文件的 page cache（页缓存）索引。即页偏移到对应 struct page 指针的映射。

这个漏洞的关键性质在于：page cache 是整个系统共享的。即使两个进程位于不同的容器、cgroup 或 user namespace 中，只要它们读取的是同一个文件系统上的同一个文件，它们就会共享同一组物理页。 一旦某个 page cache 页面被破坏，所有读取该页面的进程都会看到被破坏后的状态。

还有一点很重要。page cache 会跟踪页面是否被修改过（即 “dirty bit”，脏位）。当页面通过正常写入路径（例如 write() 或 mmap 写操作）被修改时，内核会将该页标记为 dirty，并最终把它回写到磁盘。 但接下来要看到的这种损坏，并不会经过正常的写入路径。页面从未被标记为 dirty，磁盘上的文件也完全没有变化，但所有读取该文件的进程都会得到这个已经被污染的内存版本。

Scatterlist#

内核经常需要描述跨越多个、彼此不连续的物理页的缓冲区。比如，一个 read() 返回的数据可能分散在物理内存的不同页面中；加密操作也可能需要处理分布在多个不同内存分配区域里的输入数据。scatterlist 就是内核用来表示这种“非连续缓冲区”的机制。

一个 struct scatterlist 条目描述的是一段连续的数据块：

1
2
3
4
5
6

struct scatterlist {
    unsigned long   page_link;  // struct page* | 低2位存放标志
    unsigned int    offset;     // 页内字节偏移
    unsigned int    length;     // 当前数据块长度（字节）
    dma_addr_t      dma_address;
};

page_link 字段是复用（overloaded）的。它的低 2 位用于编码标志：

  • Bit 0 (SG_CHAIN)：表示当前条目实际上是指向下一个 scatterlist 数组的指针。多个 SG（scatter-gather，内核开发者特别喜欢这种两个字母的缩写：sg、sk、mm、vm）数组就是通过这种方式串联起来的。
  • Bit 1 (SG_END)：表示这是链中的最后一个条目。

剩余的高位（屏蔽掉低 2 位之后）则存放 struct page* 指针。一个 scatterlist 链大致如下：

  | sg[0]: page_A off=0     |       | sg[0]: page_C off=128   |
  |        len=4096         |       |        len=64   [END]   |
  +-------------------------+       +-------------------------+
  | sg[1]: page_B off=0     |
  |        len=512          |
  +-------------------------+
  | sg[2]: CHAIN            |----------------+
  +-------------------------+

sg_chain() 函数负责创建这些链接。它会在一个数组最后一个条目上设置 SG_CHAIN 标志，并让它指向下一个数组的首条目。为了能够在 scatterlist 链中的某个字节偏移位置读写数据，内核提供了 scatterwalk_map_and_copy()。这个函数会逐项遍历整个链，跳过不相关的页面，直到到达目标偏移位置，然后把数据复制进去或复制出来。在这个漏洞中，最终执行“4 字节 page cache 写入”的，就是这个函数。

splice()：零拷贝 I/O#

splice() 系统调用可以在文件描述符和 pipe 之间移动数据，而无需经过 userspace 拷贝。正常情况下：

1

read() -> userspace buffer -> write()

而 splice() 不会复制数据本身，它传递的是“页面引用（page references）”。pipe 中保存的是那些仍然位于 page cache 中的物理页指针。

  | (磁盘文件)|    | (内存中) |    | (AF_ALG) |
  +----------+    +----------+    +----------+
       |               |               |
       '---------------'               |
       同一组物理页                     |
       （page cache 页面）             |
                                       |
                                  内核加密子系统
                                  在 scatterlist 中
                                  接收到这些
                                  page cache 页引用

当我们把一个文件通过 splice() 写入 pipe 时，pipe 的内部缓冲区不会得到数据副本。它拿到的是 page cache 页面本身的引用。随后，当再通过 splice() 从 pipe 写入 socket 时，socket 的内部缓冲区（在 AF_ALG 场景下是 scatterlist）会继续接收这些相同的 page cache 页面引用。

整个过程中没有任何一步发生数据拷贝。于是，内核加密子系统现在实际上持有了“指向文件 page cache 页面的直接指针”。如果没有 splice()，加密子系统处理的会是“复制后的缓冲区”。而有了 splice()，它操作的直接就是 page cache 本身。

著名的 Dirty COW 漏洞本质上用了同样的技巧：在不复制数据的情况下传播页面引用。区别在于，Dirty COW 走的是 VM fault handler 路径，而这里走的是 splice()。

AF_ALG and AEAD#

AF_ALG 是 Linux 的一种 socket family，用于把内核加密 API 暴露给非特权用户态程序。

任何普通用户都可以这样做：

1
2
3
4
5
6
7
8
9

int alg_fd = socket(AF_ALG, SOCK_SEQPACKET, 0);  // AF_ALG = 38

struct sockaddr_alg sa = {
    .salg_family = AF_ALG,
    .salg_type   = "aead",
    .salg_name   = "authencesn(hmac(sha256),cbc(aes))"
};

bind(alg_fd, (struct sockaddr *)&sa, sizeof(sa));

这里不需要 root也不需要 CAP_NET_ADMIN。对应模块也会在首次使用时自动加载。AF_ALG 的设计初衷，是让用户态应用能够直接使用内核中的硬件加速加密能力，而无需自己编写内核模块。

AEAD（Authenticated Encryption with Associated Data，带关联数据的认证加密）是一类同时提供机密性（encryption，加密）和完整性（authentication tag，认证标签）的加密算法。AAD（Associated Data，关联数据）会被认证，但不会被加密。它通常是必须防止篡改的明文元数据。Ciphertext（密文）会被解密。Authentication Tag（认证标签）则会同时基于 AAD 和 ciphertext 进行校验，以检测是否发生篡改。

一个 AEAD 解密输入通常长这样：

1
2
3
4

  +---------------+--------------------+------------------+
  | AAD           | Ciphertext         | Authentication   |
  | (仅认证)       | (解密+认证)          | Tag（校验）       |
  +---------------+--------------------+------------------+

authencesn#

authencesn（你可以这样理解这个单词，auth + enc + esn）是一种专门用于支持 IPsec ESP Extended Sequence Numbers（RFC 4303）的 AEAD 模板。每个 IPsec 数据包都会携带一个 sequence number（序列号）来防止 replay attack（重放攻击）。 最初这个序列号是 32 位计数器，但在 10 Gbps 网络下，32 位计数器不到 2 秒就会溢出。因此 RFC 4303 引入了 ESN（Extended Sequence Numbers，扩展序列号）：

一个 64 位计数器，被拆成两部分：

1
2

  完整 64 位 ESN: [ seqno_hi (32 bits) | seqno_lo (32 bits) ]
                     高32位                低32位

只有 seqno_lo 会真正出现在 ESP 数据包头中。 发送方和接收方都会维护共享状态（Security Association，SA），双方可以通过SA查询到，seqno_hi。因此 seqno_hi 是隐式存在的。 这样既能保留 64 位的 anti-replay window（防重放窗口），又能减少每个包 4 字节的网络开销。

认证哈希（authentication hash）必须覆盖完整的 64 位序列号，包括并未出现在数据包里的高位。 因此，在计算 HMAC 前，内核必须先重建完整 ESN。 在真实 IPsec ESN 解密路径（esp_input_set_header()）中，ESP 代码会从 SA / xfrm 状态中取出隐式的 seqno_hi，并把 skb header 向前扩展 4 字节。这个额外插入的 4 字节位于 SPI 和 seqno_lo 之间，然后再交给 authencesn。

  网络上传输的 ESP header:

  [  SPI  |  seqno_lo  | IV | ciphertext | tag ]

                     |
                  只有32位

扩展后，authencesn 看到的 AAD 起始布局是：

1

3
4
5

  AAD 起始布局:

    [  SPI    |  seqno_hi  |  seqno_lo  ]
       0-3       4-7          8-11
     （来自包头） （来自 SA）  （来自包头）

但 ESP 的 HMAC 规范要求哈希顺序实际上是：

1

[SPI | seqno_lo | IV | ciphertext | seqno_hi]

注意到字节顺序与当前布局不同，因此 authencesn 在计算哈希前，内核需要重新排列这些字节。它的方法是：把调用者传入的 destination buffer（dst）当成临时 scratch space（工作缓冲区）来使用。

这里主要讨论 authencesn 的解密/认证校验路径。进入 crypto_authenc_esn_decrypt() 时，调用者已经把待认证的数据放在 dst scatterlist 中；对正常 ESP 接收路径来说，dst 描述的是同一个 skb 中的 ESP 数据。下面三个 scatterwalk_map_and_copy() 调用完成 ESN 字节顺序的重排：

1
2
3
4
5
6
7
8
9

  u32 tmp[2]; 
  ...
  /* Move high-order bits of sequence number to the end. */
  // tmp[0..] = [SPI|seqno_hi]  // 正常 IPsec 路径中的语义
  scatterwalk_map_and_copy(tmp, dst, 0, 8, 0);  
  // dst[4..7] = tmp[0]  SPI
  scatterwalk_map_and_copy(tmp, dst, 4, 4, 1);  
  // dst[assoclen + cryptlen] = tmp[1]
  scatterwalk_map_and_copy(tmp + 1, dst, assoclen + cryptlen, 4, 1);

完成这三次拷贝后，authencesn 不再从 dst 的起始位置计算 HMAC，而是从 dst + 4 开始。此时从 dst + 4 看到的字节序列正好是 RFC 4303 ESN 认证所要求的顺序。

在正常 IPsec 解密路径中，tmp[1] 对应 seqno_hi，dst[assoclen + cryptlen] 原本对应报文携带的 tag 起始位置。authencesn 会临时把这个高 32 位序列号写入 tag 起始位置，把它作为隐式 ESP trailer 纳入 HMAC 输入。计算得到的 digest 存放在请求上下文的临时 buffer 中，并与报文携带的 tag 进行比较；它不是直接把新 tag 覆盖回报文。校验完成后，crypto_authenc_esn_decrypt_tail() 会从 dst[assoclen + cryptlen] 读回临时保存的 tmp[1]，恢复 dst[0..7] 的原始布局，然后再继续后续解密/返回流程。

因此，在真实 IPsec skb 接收路径里，这个临时写入通常不会留下副作用：目标区域属于内核正在处理的报文缓冲区，且恢复逻辑会把布局改回去。但这里隐含了一个关键前提：dst 必须是调用者可安全临时改写的私有缓冲区。这个前提在真实 IPsec 路径里成立，却不能自动推广到 AF_ALG 用户态接口。

The Bug#

Bug 引入: In-Place 优化#

2017年，commit 72548b093ee3引入了In-Place优化设计。

  • TX SGL (transmit scatterlist): 保存着用户写入到socket的数据。包含AAD，ciphertext和tag。用户通过sendmsg()，write() 和 splice() (pipe -> alg_socket)传入数据。如果用 splice()，TX SGL 可能不是普通内核拷贝缓冲区，而是直接引用 page cache 页面。
  • RX SGL (receive scatterlist): 保存着内核计算结果的输出数据。由内核分配内存，而不是page cache页面。

对于 AEAD 解密，用户送入 AF_ALG 的 TX SGL 通常表示完整的输入数据：

1

AAD | ciphertext | tag

72548b093ee3 为了让解密也能走 in-place 路径，在 _aead_recvmsg() 中采用了一个特殊布局：先把 AAD | ciphertext 从 TX SGL 复 制到 RX SGL，再把剩余的 tag 部分从 TX SGL 取出来，通过 sg_chain() 链到 RX SGL 末尾。

/*
  * Decryption operation - To achieve an in-place cipher
  * operation, the following  SGL structure is used:
  *
  * TX SGL: AAD || CT || Tag
  *	    |	   |	 ^
  *	    | copy |	 | Create SGL link.
  *	    v	   v	 |
  * RX SGL: AAD || CT ----+
  */

随后 AEAD 请求使用这条组合后的 scatterlist 作为输入，并把解密结果写回 RX SGL：

1
2
3
4

  rsgl_src = areq->first_rsgl.sgl.sgt.sgl;

  aead_request_set_crypt(&areq->cra_u.aead_req, rsgl_src,
              areq->first_rsgl.sgl.sgt.sgl, used, ctx->iv);  // src == dst

因此，表面上这是一次 in-place 解密。但严格来说，dst 所在的 scatterlist 链尾部并不完全属于 RX SGL 的私有缓冲区。tag 那一段仍然来自 TX SGL。

这也解释了 PoC 中写入值为什么来自用户输入，而不是真实 IPsec SA 中的 seqno_hi。AF_ALG 调用 authencesn 时并不会经过 xfrm/ESP 的 esp_input_set_header()，也不存在内核从 SA 中取出 seqno_hi 的步骤；用户提交的 AAD 会被当作 authencesn 的关联数据布局来解释。于是上面第三次 scatterwalk_map_and_copy() 写入的并不是某个真实 SA 的高 32 位序列号，而是 dst[4..7] 这 4 个字节，也就是用户可控 AAD 的第二个 32 位 word。

同时，由于 72548b093ee3 把 TX SGL 中的 tag 页面 chain 到 RX SGL 末尾，dst[assoclen + cryptlen] 这个偏移可能落在来自 TX SGL 的 tag 页面上。如果这个 tag 页面又是通过 splice() 从只读文件引入的 page cache 页面，那么 authencesn 的临时写入就变成了：

1

page_cache[target_offset] = user_controlled_aad[4..7]

这才是 Copy Fail 的核心写原语：攻击者同时控制写入位置和写入的 4 字节内容；所谓 seqno_hi 只是正常 IPsec 路径下对该 4 字节槽位的协议语义，在 AF_ALG PoC 中它实际是用户输入。
